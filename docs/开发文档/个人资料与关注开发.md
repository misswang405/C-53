# C-53 个人资料与关注开发文档

> 版本：1.0｜日期：2026-10-26｜状态：建议实施方案，未编码
> 面向：后端、前端、测试。配套：[需求文档](../需求文档/个人资料与关注需求.md)。

## 1. 现状与技术决策

- 后端当前没有 social controller、资料 controller、关注写入和列表服务。
- `UserEntity` 只有 users 现有字段；邮箱和手机号位于 `user_contacts`，不能按旧版 `docs/db/auth-schema.sql` 误建到 users。
- `MeController/AuthService.me`、`UserSummaryService` 可复用；`FollowQueryService` 接口存在但 `NoopFollowQueryService` 永远返回空关系，必须替换为数据库实现。
- Feed 的 FOLLOWING 和推荐创作者已依赖 `FollowQueryService`，替换实现后可接通，但仍要补隐私和拉黑过滤。
- 当前上传模块已有对象存储能力，但头像需要独立业务校验、对象前缀和旧文件生命周期，不能直接复制媒体正文接口。

正式模块建议：`modules/profile` 负责资料/主页，`modules/social` 负责关注关系；跨模块通过 `UserSummaryService`、`FollowQueryService`、可见性策略接口协作，不直接注入对方 Repository。

实际项目若以 MyBatis-Plus Mapper 为主，则按现有 auth/post 的 style 使用 Mapper，不同时引入另一套 DAO。Controller 正式路径沿 `/api/v1`，对应 F1–F9；权限在 SecurityConfig 中显式区分公开 GET、需认证写入与个人列表。

扩展 `UserSummaryService` 仅当需要新增摘要字段时进行；关系输出统一使用 FollowQueryService 的 FOLLOWING/FOLLOWED_BY/MUTUAL/NONE。

## 3. 数据库设计

新增 `db/profile/profile-schema.sql`：

- `user_profiles(user_id PK/FK, real_name, gender, birth_date, region, city, address, bio, created_at, updated_at, version)`。
- `user_profile` 中不重复存 username/nickname/avatar/profession/contact；这些仍由 users/user_contacts 提供。
- `user_follows(follower_id, following_id, created_at, deleted_at)`，唯一有效关系建议使用 MySQL 生成列或事务条件写入，索引 `(follower_id, created_at, following_id)`、`(following_id, created_at, follower_id)`。

如使用软删关系，恢复关注与取消关注必须在事务内条件更新，不能同时插入出重复有效关系。数据库外键是否启用要与现有脚本一致；统一由应用确保 deleted user 不再有有效关系。新增脚本追加到 `spring.sql.init.schema-locations`，存量部署必须独立迁移，`CREATE IF NOT EXISTS` 不能替代约束迁移。

stats 不建议实时冗余初版：postCount 可按 post service 聚合或缓存，follower/following 用关系表 count；性能达到阈值后再加计数表/事件修正。viewCount 无现有来源，暂不存假值。

## 4. 资料实现

### 4.1 F1/F2

F1 由 ProfileService 组装 users、user_profiles、user_contacts 和统计，并用 viewer/目标决定字段脱敏。F2 使用版本号或字段级更新：锁定用户/资料行，校验用户名唯一性，再更新 users 与 profile；username 变更要记录审计并考虑会话/缓存失效。联系方式只读，变更走未来 contact verification service。

避免从 `UserResponse` 反向推断完整资料；新增 `ProfileView` 与 `PublicProfileView` DTO，明确本人/公开字段，禁止把 `UserEntity` 直接序列化。

### 4.2 F3

头像流程：读取 multipart → 服务器端检查大小、内容类型和像素 → 解码重编码 → 对象存储写入临时/正式 key → 事务更新 avatar key/version → 异步删除旧对象。若 DB 更新失败删除新对象；若旧对象删除失败进入清理任务。返回短期签名 `avatarUrl`，数据库保存 key 而不是签名 URL。

使用独立 `profile/avatar/{userId}/...` 前缀，明确谁可读；不让 `MediaCleanupJob` 删除头像。

### 4.3 F4/F5

F4 只返回经过 VisibilityService 和 BlockService 的可见资料。F5 复用 PostService 的已发布列表查询，但入口必须传 viewer，不能直接拼 repository；应用关系/隐私后再返回动态。

## 5. 关注实现

PUT/DELETE 统一走 FollowService：验证 active viewer、禁止自己、检查目标、block 和隐私策略；对有效唯一关系做条件写入。PUT 已存在返回 true，DELETE 不存在返回 false，均重新查询双向关系和统计，不按旧前端值推算。

写入事务内维护关系行；更新 feed/recommendation 缓存使用提交后事件，缓存失败不回滚关系，但读取必须有数据库降级。`findFollowingIds` 的 Noop 实现替换为按 active relationship 查询；对大集合使用批量/临时表或分页，不把全部 ID 无界加载进内存。

F6/F7 以关系创建时间和用户 ID组成稳定游标，批量调用 UserSummaryService，过滤已删除/不可见/拉黑用户后返回 `items,nextCursor`。关系总数可单独返回 stats，但列表查询不使用 count 作为分页判断。

## 6. 可见性与跨模块协作

新增 `VisibilityService`/`BlockService` 接口，至少提供 `canViewProfile(viewer,target)`、`canViewPost`、`canListFollowing`、`canInteract`。不要让每个 Controller 自行解析 PUBLIC/FRIENDS/PRIVATE。

接入点：Feed、PostService.get/list、Interaction 评论/回复、推荐创作者、Profile F4/F5/F6/F7、私信会话创建/读取、通知列表。隐私模块实现后通过同一服务读取设置；在设置模块未上线前，采用明确默认值并记录 feature flag，禁止局部接口先“猜权限”。

拉黑规则的实际写入由设置/安全模块补充，但 Profile/Follow 服务必须依赖接口而不是查询不存在的表。拉黑事件后解除关系、隐藏内容和终止会话采用领域事件，避免跨模块互相注入 Repository。

## 7. 前端改造

- `loadPrivateData` 与 profile 页面切换为真实 ProfileView/stats，不再用 ConnectionsPanel 硬编码数字。
- 资料保存成功后以服务端对象替换本地；对 `null` 字段保留空表单默认值。
- 头像上传显示处理中、失败可重试，避免重复提交；成功更新 profile/avatar cache。
- 成员主页请求增加 request sequence，资料和帖子分开呈现失败状态。
- 列表保存 cursor 并实现加载更多；follow 成功回写双方布尔值和局部计数。
- 从资料/关注列表预留“发消息”事件，但在私信模块完成前不发送不存在的请求。

## 8. 测试方案

后端单元测试：字段校验、脱敏、username 并发唯一性、关系状态矩阵、自己关注、重复 PUT/DELETE、Noop 替换后的 feed/recommendation。

集成测试：真实 MySQL 约束和游标、资料与 users/contact 事务、头像对象 DB 失败补偿、隐私/拉黑跨模块、撤销会话后的访问。使用 Testcontainers 或项目现有集成方式，不能只 mock repository 声称覆盖数据库约束。

前端测试：空值资料、慢请求乱序、图片失败、列表 cursor、连续关注点击、切账号缓存隔离。

## 9. 开发顺序与上线

1. 先建 profile/social schema 与迁移校验，补 UserSummary/FollowQuery 的真实实现。
2. 实现资料读写、头像安全链路，再实现关注写入和分页。
3. 接入 feed/recommendation，之后接 Visibility/Block 策略。
4. 前端消除硬编码、接入分页和关系状态，完成权限回归。
5. 灰度关注写操作和资料编辑，监控重复关系冲突、对象孤儿、列表延迟和权限拒绝。

回滚先关闭写入口并保留新增数据兼容读取；若回退代码，不删除用户资料/关注关系表，不恢复硬编码统计覆盖真实数据。数据库降级需另行制定可逆迁移，不能直接 drop。
