# C-53 私信与通知开发文档

> 版本：1.0｜日期：2026-10-26｜状态：建议实施方案，未编码
> 面向：后端、前端、测试、运维。配套：[需求文档](../需求文档/私信与通知需求.md)。

## 1. 当前代码事实

- 后端 Controller 清单中没有 conversations、messages、notifications。
- 前端 `api.js` 已定义 G1–G6；`App.vue` 进入消息页拉会话，选中会话拉消息并调用已读，发送传 `clientMessageId/type/content`。
- 消息页“+”和更多菜单目前无业务事件，需增加创建会话和会话操作设计，不能仅补后端接口就宣称流程完成。
- `AuthServiceImpl.me` 的 unread 当前固定为 0；需要接入未读查询，不能在前端本地长期维护权威未读数。
- 现有认证、动态、互动模块已有 Service 边界；新模块不得直接访问其它模块 Repository。

若项目不采用事件总线，首版可用事务 outbox：动态/互动/关注模块只写领域事件，由通知 worker 消费；禁止在点赞/评论事务中直接调用通知 Repository，避免跨模块事务耦合。

正式 Controller 路径按清单使用 `/api/v1/conversations`、`/api/v1/notifications`；创建会话另加 `POST /api/v1/conversations`。

## 3. 数据库设计

新增 `db/messaging/messaging-schema.sql`：

- `conversations(id, participant_low_id, participant_high_id, created_at, updated_at, last_message_id, deleted_at)`，唯一 `(participant_low_id,participant_high_id)`，成员排序后写入。
- `messages(id, conversation_id, sender_id, client_message_id, type, content, created_at, deleted_at)`，唯一 `(conversation_id,sender_id,client_message_id)`，索引 `(conversation_id,created_at,id)`。
- `conversation_reads(conversation_id,user_id,last_read_at,last_read_message_id,updated_at)`，唯一二元键。

新增 `db/notification/notification-schema.sql`：

- `notifications(id, recipient_id, actor_id, type, preview, target_type, target_id, created_at, read_at, dedupe_key)`，索引 `(recipient_id,read_at,created_at,id)` 和唯一业务去重键（按通知类型定义）。
- 大量预览或数据导出使用对象/事件引用，不把完整私密正文写进通知表。

脚本追加 `spring.sql.init.schema-locations` 仅适合开发初始化；生产必须用版本化迁移。数据库唯一键是幂等最后防线，服务层仍需查询以返回 200/201 语义。

## 4. 服务实现

### 4.1 创建会话

按两个用户 ID 规范排序，事务内先查后插并捕获唯一键竞争，成功后返回同一会话。创建前调用 UserSummary/Follow/Visibility/Block 接口检查目标和消息权限。返回会话摘要，不返回历史私信正文。

### 4.2 发送消息

事务内：锁定会话 → 校验成员、账号状态、设置和拉黑 → 按 sender+clientMessageId 查已有消息 → 相同内容返回原消息，冲突返回 409 → 插入消息 → 更新会话摘要/last_message_id → 更新接收方 unread 原子值/写事件 outbox。通知事件使用 dedupe key（conversation/message ID）。

消息正文使用与 `ContentRules` 同类的纯文本校验，但独立配置 2000 码点上限；不要复用发布 600 码点常量造成隐式产品约束。敏感内容过滤若未来接入，必须保持错误码稳定。

### 4.3 分页和已读

消息按 `(created_at,id)` 组成稳定游标；查询多一条判断 nextCursor。向前端返回的方向需和 UI 明确，首版可后端倒序、前端 reverse，续页合并必须固定策略。G4 锁定当前用户 read row，取当前会话最后已知消息 ID 更新；不能依赖客户端传来的“读到哪里”，否则可能误清未来消息。

通知采用相同稳定游标；G6 按 recipient 条件更新 `read_at IS NULL`。所有查询用 recipient/member 条件，资源 ID 猜测只返回通用 404/403。

## 5. 未读数与通知事件

实现 `UnreadQueryService`，由 `AuthServiceImpl.me` 调用，返回消息和通知未读。首次可分别 count/read row；高并发后用 Redis 计数 + 数据库校正，但数据库最终状态必须权威。

事件来源：

- FollowService：新关注/回关。
- InteractionService：评论、回复、可选分享。
- MessageService：新消息。
- Profile/系统：数据导出完成、账号安全事件。

事件必须在业务事务提交后投递；通知消费至少一次，依靠 dedupe_key 幂等。actor/target 可能已删除，生成时保存最小安全快照，读取时再次脱敏。队列失败进入重试和死信，不能让主业务请求同步等待。

## 6. 权限与隐私集成

新增 `MessagingPolicy` 依赖 `SettingsQueryService`、`FollowQueryService`、`BlockQueryService`、用户状态服务。接收方设置优先：EVERYONE/FOLLOWING/MUTUAL/NONE；发起新会话和已存在会话继续发送都检查策略，最终规则由产品确认是否允许“关系变化后保留已存在会话”。

消息与通知读取不得依赖前端传来的 owner；会话成员由数据库关系判断。通知目标点击时调用已有资源权限校验，不把 targetId 直接当成授权。

## 7. 前端改造

- 增加创建会话 API 和从 MemberProfile/ConnectionsPanel 的“发消息”入口，消息页“+”打开用户选择。
- `loadMessages` 保存 cursor 和加载状态，合并而不是覆盖本地发送结果。
- 发送失败不从列表移除已确认消息；未确认消息不显示为成功。
- 进入会话顺序为加载/展示成功后调用 read；当前 Promise.all 失败时分别显示错误。
- 通知列表保存未读状态和 cursor；全部已读成功后再更新本地，不因网络失败清空列表。
- 账号切换/退出清理会话、通知和未读缓存；通知目标路由前再次检查权限。
- 首期不接 WebSocket，预留 refresh/轮询入口，避免假装实时。

## 8. 测试方案

后端单元：权限矩阵、成员判断、文本校验、游标、幂等键、未读增减和通知 dedupe。集成：唯一会话竞争、重复消息、数据库回滚、outbox 重试、真实 MySQL 索引、用户停用/删除。

端到端：两用户创建同一会话、双向发送、刷新继续、进入会话已读、通知生成和全部已读；游客/非成员/拉黑/FOLLOWING/MUTUAL/NONE 全矩阵。并发测试验证一个 clientMessageId 只有一条消息和一份未读。

前端：空会话、无入口、慢请求乱序、发送失败重试、分页、切账号和通知失败不误清空。测试不得使用真实手机号、邮箱或生产消息。

## 9. 开发顺序与上线

1. 先落表和 outbox/事件基础、UnreadQueryService。
2. 实现会话创建/查询、消息幂等发送、消息分页和已读。
3. 接入设置/关注/拉黑策略，再实现通知生产与列表。
4. A11 接入真实未读数，前端补齐发起会话和可靠状态。
5. 灰度发送入口，监控发送成功率、幂等冲突、队列延迟、未读负数和权限拒绝。

回滚时关闭发送/创建入口，保留只读兼容查询；不删除历史消息和通知。若事件消费者回滚，必须停止重复消费或保持 dedupe 兼容。
