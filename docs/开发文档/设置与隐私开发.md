# C-53 设置与隐私开发文档

> 版本：1.0｜日期：2026-10-26｜状态：建议实施方案，未编码
> 面向：后端、前端、测试、运维。配套：[需求文档](../需求文档/设置与隐私需求.md)。

## 1. 当前代码与设计原则

- 前端已定义 H1–H10、350ms 防抖 PATCH、黑名单移除、授权撤销和数据导出调用；后端没有 settings/profile/privacy controller。
- `auth_user_agreements` 只记录社区公约/隐私政策同意，不是 OAuth authorized apps；不能复用成授权表。
- `App.vue` 开启 private 时先修改本地 visibility，再异步 PATCH；后端必须定义原子语义，不能让 UI 顺序决定最终权限。
- 当前 Spring SQL 初始化只加载 auth、post、interaction schema；新增模块需要独立脚本和生产迁移。
- 安全原则：策略集中、默认收紧、缓存故障不放开、Controller 不自行判断权限。

建议新增 `modules/settings`，按职责拆分 settings storage、visibility policy、block、authorization、export；提供接口给 profile/social/post/interaction/messaging/discovery，而不是互相注入 Repository。

## 3. 数据库设计

新增 `db/settings/settings-schema.sql`：

- `user_settings(user_id PK, visibility_profile/posts/bookmarks/following_list, social_messages/comments/mentions, personalized_content/ads, mode_teen/elder/private, private_backup_json, version, created_at, updated_at)`。
- `blocked_users(owner_id, blocked_user_id, created_at, deleted_at, reason)`，有效关系唯一，双向读取策略由服务统一定义。
- `authorized_app_grants(id, user_id, client_id, app_name, scopes_json, created_at, last_used_at, revoked_at)`；client_id 应来自可信 OAuth 注册，不存 client secret。
- `data_export_tasks(id, user_id, status, requested_at, started_at, finished_at, expires_at, object_key, error_code, attempt_count)`；object key 不直接返回给客户端。
- 若采用通用 outbox，增加 settings_changed、block_changed、export_completed 事件，不把队列 payload 放入用户敏感原文。

枚举在数据库可以用 CHECK，但 MySQL 5.7 可能不执行 CHECK，应用层必须校验。新增 schema 必须纳入开发初始化和生产迁移；存量 `CREATE IF NOT EXISTS` 不会变更已有约束。

## 4. 设置保存和版本

H1 读取不存在的设置时返回默认并可惰性创建。H2–H5 采用整组覆盖：请求 DTO 所需字段全部存在，统一规范化后在一个事务中校验并更新。事务内锁 user_settings 行，检查 version（若协议启用），更新 version；冲突返回 409 并带最新版本，不返回其他用户信息。

私密模式切换必须在一次事务内完成：

- 开启：将当前 visibility 原值写入 `private_backup_json`，再把四项有效策略设为 PRIVATE。
- private 已开启时修改 visibility：按产品决定拒绝或更新备份；建议允许并同步更新备份，但外部有效值仍为 PRIVATE。
- 关闭：从备份恢复经过当前枚举校验的值；备份不存在使用安全默认 PRIVATE/PUBLIC 组合，并清理备份。
- PATCH modes 同时设置 teen/elder 时返回冲突；禁止由前端调用顺序产生短暂放开窗口。

recommendations 只影响内容选择和广告个性化，不关闭系统安全/交易通知。保存成功后失效 `settings:{userId}` 缓存和相关 feed/profile 缓存；失效失败不能回滚设置，也不能继续使用旧策略放行，读取时版本校验或回源。

## 5. 统一隐私策略

实现 `VisibilityService`：

- `canViewProfile(viewer,target)`
- `canViewPost(viewer,post/author)`
- `canViewBookmarks(viewer,target)`
- `canViewFollowingList(viewer,target)`
- `canInteract(viewer,target,type)`
- `canReceiveMessage(recipient,sender)`

输入必须包含 viewer（可为空）、target、关系和 block 状态；不能接受“前端已过滤”的布尔值作为授权依据。所有默认值由 SettingsService 提供。查询列表先在数据库过滤可见用户/动态，内存过滤只能作为补漏，不能导致分页短页和隐私侧信道。

跨模块接入：PostService/feed/recommendation、InteractionService 评论/提及、Profile/Follows、Messaging 会话和 Notification 读取。每处统一处理 PRIVATE/FOLLOWING/MUTUAL/NONE 和 block；资源不可见时使用一致的 404/空列表策略，避免枚举。

## 6. 黑名单和授权

`PUT /me/blocked-users/{id}` 与 H7 由 BlockService 事务处理：验证目标、写有效关系、解除 follow、写 block_changed 事件。消费者使 profile/feed/recommendation/message cache 失效；消息和历史内容策略由 MessagingPolicy 判断。取消拉黑不自动重建 follow。

H8/H9 只读写 `authorized_app_grants`。撤销事务更新 revoked_at 并发布 grant_revoked；OAuth token introspection/refresh 必须检查 grant 状态。当前没有 OAuth 授权发起链路，先提供空列表和接口骨架会掩盖缺陷，不建议这样交付；应明确功能开关，只有真实写入来源存在时开放 H8/H9。

## 7. 数据导出

H10 事务创建 PENDING task 和唯一幂等键（建议按 user+时间窗口/客户端键），提交后 worker 抢占任务。导出 worker 通过各模块只读 Service 获取本人数据，不能直接复制所有 Repository 或绕过隐私过滤。文件加密写入隔离对象存储，返回 taskId/status，不返回永久 URL。

状态：PENDING/RUNNING/SUCCEEDED/FAILED/EXPIRED。完成写 notification outbox；下载接口若后续增加需校验 userId、状态、expiresAt、一次性 nonce。失败指数退避、有限重试、死信告警；任务和文件过期清理使用独立 Job。

## 8. 前端改造

- 保留设置组防抖，但保存队列必须按组串行/取消旧请求，成功后才提交本地“已保存”状态；失败恢复服务端快照或显式标红。
- private 开关改为一次 H5 原子操作后刷新 H1/H2 状态，不在 watch 中发出可能乱序的多组覆盖请求。
- blocked 列表补充真正拉黑入口；移出成功后再更新本地，不因失败移除行。
- authorized apps 无数据时显示“尚无第三方授权”，不把系统权限/协议同意映射过来。
- export 显示 taskId 状态，通知到达后显示下载入口；不能只把列表清空或提示“将通过通知完成”。
- 账号切换和退出清除设置/权限缓存；服务端仍需每次校验。

## 9. 测试方案

后端单元：默认值、枚举、模式互斥、私密备份恢复、版本冲突、权限矩阵、阻断规则、导出状态机。集成：真实 MySQL 迁移/唯一约束、并发 PATCH、缓存失效失败、block 与 follow 事务、授权撤销影响 token、worker 重试。

跨模块：匿名/本人/普通他人/关注/互关/拉黑/停用用户访问 profile、post、feed、comments、messages、notifications；private 开关瞬间不能放开；teen/elder 绕过 UI 请求被拒。

前端：防抖乱序、失败恢复、私密切换、空列表、导出失败/过期、切账号缓存隔离。安全测试检查设置接口不接受中文值、导出不泄露他人数据、日志无 token/联系方式。

## 10. 开发顺序、上线与回滚

1. 先落设置表、SettingsService、VisibilityService 和 BlockQuery 接口，补策略单测。
2. 接入资料/关注、动态/feed/互动；权限矩阵通过后接私信/通知。
3. 实现黑名单写入、授权真实来源、导出 worker 和通知。
4. 前端改为原子模式切换、可靠保存和任务状态。
5. 灰度策略读取（先 shadow compare 旧/新结果），再开放写入；监控 403/404 比例、缓存命中、导出积压、策略异常。

回滚先关闭写入口或功能开关，保留策略读兼容；数据库表和设置数据不删除。若策略服务异常，受保护资源默认拒绝/返回维护错误，不能回退为 PUBLIC。迁移需有备份和可验证恢复演练。
