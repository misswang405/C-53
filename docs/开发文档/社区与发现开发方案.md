## 1. 评审摘要

| 项目 | 结论 |
|---|---|
| 交付内容 | 3 个新接口 + 1 个已有接口的字段修复 + 在线人数统计 + 前端 4 处改造 |
| 后端新增模块 | `com.c53.modules.discovery`（社区概况、推荐创作者）；`feed` 归入现有 `post` 模块 |
| 数据库 | 不新增表；`posts` 新增 1 个复合索引 |
| Redis | 新增 3 类键：在线 ZSET、在线节流、推荐创作者池 |
| 对现有代码的侵入 | `PostResponse` 增 4 个字段；`JwtAuthenticationFilter` 增一次在线写入；`SecurityConfig` 增显式路由 |
| 前端契约破坏 | 无；只修 `normalizeTopic` 字段读取、增加登录拦截与展示截断 |
| 主要风险 | 关注表未实现导致关注流为空；互动数据缺失导致推荐得分退化；在线写入影响鉴权耗时 |
| 预估工期 | 7 人日 |

**本方案的核心取舍**

1. 信息流读取放在 `post` 模块，因为它复用动态查询、游标、媒体批量加载和视图组装；不新建一套重复的数据访问。
2. 推荐与在线统计放在新的 `discovery` 模块，避免 `post` 模块继续膨胀。
3. 关注关系、拉黑关系通过**接口 + 空实现**接入，关注模块上线后替换实现即可，不改信息流代码。
4. 本期不引入 Caffeine、推荐引擎、消息队列；只使用 Redis + MySQL。

## 2. 决策基线

### 2.1 承接 PRD 的决策

| # | 决策 | 落地方式 |
|---|---|---|
| Q1 | 关注流本期上线，关注表未实现时返回空列表 | `FollowQueryService` 空实现返回空集合 |
| Q2 | 推荐流与最新流必须有差异 | 推荐流按 9.4 的规则打分排序 |
| Q3 | 推荐流排除自己 | 登录态候选池过滤 `authorId = currentUserId` |
| Q4 | 本期不做无限滚动 | 推荐流 `nextCursor = null`；前端只请求首屏 |
| Q5 | 互动字段本期返回 0 / false | `PostResponse` 增字段，值固定 |
| Q6 | 话题字段统一为 `postCount` | 修改前端 `normalizeTopic`，后端不动 |
| Q7 | 在线口径：5 分钟窗口 + 60 秒节流 | Redis ZSET + `SET NX EX 60` 节流 |
| Q8 | 推荐创作者固定 6 条 | `limit = 6`，首页前端截前 3 条 |
| Q9 | 拉黑本期不实现，预留过滤点 | `FeedServiceImpl` 保留 `filterHidden` 方法，返回原列表 |
| Q10 | 匿名限流 60 次/分钟 | 复用 `RedisRateLimiter` |
| Q11 | 热门话题本期不缓存 | 直接查 `idx_topics_status_count` |
| Q12 | 推荐池缓存不区分登录态 | 公共池缓存 5 分钟，请求时应用层过滤 |

### 2.2 本方案新增的工程决策

| # | 决策 | 理由 | 备选 |
|---|---|---|---|
| E1 | `FeedController` / `FeedService` 放在 `modules/post` | 复用 `PostRepository`、`toResponses`、`CursorCodec`，避免跨模块暴露实体 | 新建 `discovery` 内的 feed 服务，需要复制查询与视图组装 |
| E2 | 新增 `modules/discovery` 承载 `community` 与 `creator` | 两个能力都以只读聚合为主，边界清晰 | 分别新建 `community`、`creator` 两个模块（文件过碎） |
| E3 | 在线统计通过 `common.presence.OnlinePresenceRecorder` 接口接入安全过滤器 | `security` 包不得反向依赖业务模块（目录规范第 4 条） | 在 `security` 里直接注入 `discovery` 的 Store（违反分层） |
| E4 | 关注关系定义 `modules/social/service/FollowQueryService`，本期提供空实现 | 3.6 模块未实现，但接口可以先冻结 | 在 feed 里硬编码空集合（后续改动大） |
| E5 | 作者状态过滤在应用层完成：新增 `UserSummaryService.findActiveUserIds` | 避免 `posts` 查询跨表 join `users`，保持模块边界 | SQL 中 `EXISTS` 子查询（耦合更强） |
| E6 | 推荐创作者候选通过 `UserSummaryService.findActiveCandidates` + `PostService.countPublishedSince` 获取 | 不直接查对方表；两个方法都可复用 | discovery 自建 Mapper 跨表查询（边界模糊） |
| E7 | Redis Key 统一 `discovery:` 前缀 | 与现有 `auth:`、`post:` 前缀一致 | PRD 中的 `c53:community:*` 只是示意，落地改用模块前缀 |
| E8 | 索引变更写成幂等 SQL | `spring.sql.init.mode=always`，脚本每次启动执行，重复 `ALTER` 会导致启动失败 | 手工执行 DBA 脚本（不利于新环境初始化） |
| E9 | 推荐流候选池每次请求重新计算，不缓存 | 500 条以内计算量小；避免缓存与发布状态不一致 | Redis 缓存候选 ID（增加失效逻辑） |
| E10 | 新增 `common.ClientIp` 工具，`AuthController` 改为复用 | 限流需要 IP，现有实现是 Controller 私有方法 | 各处复制 IP 解析逻辑 |

## 6. 数据与索引

### 6.1 索引变更

`posts` 现有索引：

- `idx_posts_feed (status, published_at, id)`：适配 `LATEST`。
- `idx_posts_author_status_updated (author_id, status, updated_at)`：适配“我的发布”。

关注流按 `author_id IN (...) AND status = 'PUBLISHED' ORDER BY published_at DESC, id DESC` 查询，现有索引无法覆盖排序，需要新增：

```sql
ALTER TABLE posts
    ADD INDEX idx_posts_author_status_published (author_id, status, published_at, id);
```

### 6.2 幂等执行脚本

由于 `spring.sql.init.mode=always` 且 `continue-on-error=false`，脚本每次启动都会执行。直接写 `ALTER TABLE` 会在第二次启动时报“索引已存在”。在 `db/post/post-schema.sql` 末尾追加幂等块：

```sql
-- 关注流索引：幂等创建，避免每次启动重复 ALTER 失败
SET @idx_exists := (
    SELECT COUNT(*) FROM information_schema.statistics
    WHERE table_schema = DATABASE()
      AND table_name = 'posts'
      AND index_name = 'idx_posts_author_status_published'
);
SET @ddl := IF(
    @idx_exists = 0,
    'ALTER TABLE posts ADD INDEX idx_posts_author_status_published (author_id, status, published_at, id)',
    'SELECT 1'
);
PREPARE stmt FROM @ddl;
EXECUTE stmt;
DEALLOCATE PREPARE stmt;
```

> 验证：连续启动两次应用，第二次不得报错；`SHOW INDEX FROM posts` 中该索引只出现一次。

### 6.3 查询与索引匹配

| 查询 | SQL 条件 | 使用索引 |
|---|---|---|
| 最新流 | `status='PUBLISHED' AND deleted_at IS NULL ORDER BY published_at DESC, id DESC` | `idx_posts_feed` |
| 关注流 | `author_id IN (...) AND status='PUBLISHED' AND deleted_at IS NULL ORDER BY published_at DESC, id DESC` | `idx_posts_author_status_published` |
| 推荐候选 | `status='PUBLISHED' AND deleted_at IS NULL AND published_at >= ? ORDER BY published_at DESC LIMIT 500` | `idx_posts_feed` |
| 作者近 30 天发布数 | `author_id IN (...) AND status='PUBLISHED' AND published_at >= ? GROUP BY author_id` | `idx_posts_author_status_published` |
| 热门话题 | `status='ACTIVE' ORDER BY post_count DESC, id ASC LIMIT ?` | `idx_topics_status_count` |
| 推荐创作者候选 | `users.status='ACTIVE' AND deleted_at IS NULL ORDER BY updated_at DESC LIMIT ?` | 建议补 `idx_users_status_updated (status, updated_at)`（可选，用户量小时可后置） |

### 6.4 数据约定

- 不新增表、不新增字段。
- 互动字段为接口层占位，不落库。
- 在线统计只存 Redis，不落库。

    RECOMMENDED,
    FOLLOWING,
    LATEST;

    public static FeedScope parse(String raw) {
        if (raw == null || raw.isBlank()) {
            return RECOMMENDED;
        }
        try {
            return valueOf(raw.trim().toUpperCase(Locale.ROOT));
        } catch (IllegalArgumentException exception) {
            throw ApiException.badRequest("VALIDATION_ERROR", "信息流范围不合法");
        }
    }
}

| 场景 | HTTP | code | message |
|---|---|---|---|
| `scope` 非法 | 400 | `VALIDATION_ERROR` | 信息流范围不合法 |
| `cursor` 非法 / 过长 | 400 | `VALIDATION_ERROR` | 分页游标不合法 |

## 9. 核心流程设计

### 9.1 Feed 总流程

```java
@Override
public PostListResponse feed(AuthPrincipal principal, String scope, String cursor, int limit) {
    FeedScope feedScope = FeedScope.parse(scope);
    int size = normalizeLimit(limit);

    if (feedScope == FeedScope.FOLLOWING) {
        requireLogin(principal);
    }
    enforceFeedRateLimit(principal);
    validateCursorLength(cursor);

    return switch (feedScope) {
        case LATEST -> latest(principal, cursor, size);
        case FOLLOWING -> following(principal, cursor, size);
        case RECOMMENDED -> recommended(principal, size);
    };
}
```

**公共规则**

- `limit`：`<=0` → 20，`>50` → 50。
- `cursor`：长度 > 256 直接 400；解码失败使用 `CursorCodec` 的既有异常。
- 限流键：登录用 `discovery:rate:feed:user:{userId}`（120 次/分钟），匿名用 `discovery:rate:feed:ip:{ip}`（60 次/分钟）。
- 所有查询强制 `status='PUBLISHED'`、`deleted_at IS NULL`。

public List<PostEntity> findLatest(Instant cursorTime, String cursorId, int limit) {
    LambdaQueryWrapper<PostEntity> wrapper = Wrappers.<PostEntity>lambdaQuery()
            .eq(PostEntity::getStatus, PostStatus.PUBLISHED)
            .isNull(PostEntity::getDeletedAt);

                        .lt(PostEntity::getId, cursorId)));

            .orderByDesc(PostEntity::getPublishedAt)
            .orderByDesc(PostEntity::getId)
            .last("LIMIT " + limit));

                                   AuthPrincipal principal,
                                   Function<PostEntity, Instant> timeExtractor) {
    boolean hasMore = rows.size() > size;
    List<PostEntity> page = hasMore ? rows.subList(0, size) : rows;
    List<PostEntity> visible = filterInactiveAuthors(page);
    List<PostResponse> items = toResponses(visible, principal);

        PostEntity last = page.get(page.size() - 1);
        nextCursor = CursorCodec.encode(timeExtractor.apply(last), last.getId());
    }
    return new PostListResponse(items, nextCursor);
}

#### 9.4.3 打分实现

```java
public final class RecommendationScorer {

    private static final double TIME_WEIGHT = 0.60;
    private static final double TOPIC_WEIGHT = 0.25;
    private static final double AUTHOR_WEIGHT = 0.15;

    public double score(PostEntity post, ScoreContext context, Instant now) {
        double timeScore = timeScore(post.getPublishedAt(), now);
        double topicScore = topicScore(post.getTopicId(), context);
        double authorScore = authorScore(post.getAuthorId(), context);
        return TIME_WEIGHT * timeScore
                + TOPIC_WEIGHT * topicScore
                + AUTHOR_WEIGHT * authorScore;
    }

    private double timeScore(Instant publishedAt, Instant now) {
        if (publishedAt == null) return 0;
        double ageHours = Duration.between(publishedAt, now).toMinutes() / 60.0;
        return Math.exp(-ageHours / 24.0);
    }

    private double topicScore(String topicId, ScoreContext context) {
        if (topicId == null || context.maxTopicCount() <= 0) return 0;
        TopicSummary topic = context.topics().get(topicId);
        if (topic == null) return 0;
        return Math.min(1.0, topic.postCount() / (double) context.maxTopicCount());
    }

    private double authorScore(String authorId, ScoreContext context) {
        UserScoringProfile profile = context.profiles().get(authorId);
        if (profile == null) return 0;
        double score = 0;
        if (notBlank(profile.avatarUrl())) score += 0.4;
        if (notBlank(profile.bio())) score += 0.3;
        if (notBlank(profile.profession())) score += 0.3;
        return score;
    }
}
```

**排序与作者密度**

```java
public List<PostEntity> rank(List<PostEntity> candidates, ScoreContext context, Instant now) {
    List<ScoredPost> scored = candidates.stream()
            .map(post -> new ScoredPost(post, score(post, context, now)))
            .sorted(Comparator.comparingDouble(ScoredPost::score).reversed()
                    .thenComparing(item -> item.post().getPublishedAt(), Comparator.reverseOrder())
                    .thenComparing(item -> item.post().getId(), Comparator.reverseOrder()))
            .toList();
    return applyAuthorStreak(scored, maxAuthorStreak);
}

private List<PostEntity> applyAuthorStreak(List<ScoredPost> scored, int maxStreak) {
    List<PostEntity> result = new ArrayList<>();
    Map<String, Integer> streak = new HashMap<>();
    List<PostEntity> deferred = new ArrayList<>();
    for (ScoredPost item : scored) {
        int count = streak.getOrDefault(item.post().getAuthorId(), 0);
        if (count >= maxStreak) {
            deferred.add(item.post());
            continue;
        }
        result.add(item.post());
        streak.merge(item.post().getAuthorId(), 1, Integer::sum);
    }
    // 候选不足时放宽密度限制，避免列表过短
    result.addAll(deferred);
    return result;
}
```

> 说明：分数相同时按 `publishedAt`、`id` 稳定排序，保证同一次请求结果确定。

### 9.7 在线人数

**写入**

```java
public final class RedisOnlinePresenceStore implements OnlinePresenceRecorder {

    private static final String ONLINE_KEY = "discovery:online";
    private static final String TOUCH_PREFIX = "discovery:online:touch:";

    @Override
    public void touch(String userId) {
        long now = System.currentTimeMillis();
        try {
            Boolean first = redis.opsForValue().setIfAbsent(
                    TOUCH_PREFIX + userId, "1", properties.getOnline().getTouchInterval());
            if (!Boolean.TRUE.equals(first)) {
                return;
            }
            redis.opsForZSet().add(ONLINE_KEY, userId, now);
            long cutoff = now - properties.getOnline().getWindow().toMillis();
            redis.opsForZSet().removeRangeByScore(ONLINE_KEY, 0, cutoff);
        } catch (RuntimeException exception) {
            log.warn("online presence touch failed userId={}", userId, exception);
        }
    }
}
```

**查询**

```java
public long count() {
    try {
        long now = System.currentTimeMillis();
        long cutoff = now - properties.getOnline().getWindow().toMillis();
        Long count = redis.opsForZSet().count(ONLINE_KEY, cutoff, Double.POSITIVE_INFINITY);
        long value = count == null ? 0 : count;
        if (value < 0 || value > properties.getOnline().getMaxCount()) {
            log.warn("online count abnormal value={}", value);
            return 0;
        }
        return value;
    } catch (RuntimeException exception) {
        log.warn("online count unavailable", exception);
        return 0;
    }
}
```

**接入点**

`JwtAuthenticationFilter` 构造注入 `OnlinePresenceRecorder`，认证成功后：

```java
if (onlinePresenceRecorder != null) {
    onlinePresenceRecorder.touch(claims.userId());
}
```

- `touch` 内部吞掉所有 Redis 异常，不阻断请求。
- 为避免每次请求都进行完整 Redis 交互，`setIfAbsent` 失败时直接返回。
- `RedisOnlinePresenceStore` 内部对 Redis 操作设置 50ms 超时（通过配置连接超时，或使用 `CompletableFuture` 包装）。

**与 PRD 的差异说明**

PRD 6.4.3 建议节流使用进程内 Map。本方案改用 Redis `SET NX EX 60`，原因：

1. 避免本地 Map 无界增长与多实例不一致。
2. 每用户每分钟最多一次 ZSET 写入，Redis 压力可控。
3. 实现更简单，无额外过期清理任务。

## 11. 权限与安全

### 11.1 `SecurityConfig` 变更

现有配置对未知路径 `permitAll()`。为避免后续收紧时遗漏，显式声明只读接口：

```java
.authorizeHttpRequests(authorize -> authorize
        // ... 现有规则 ...
        .requestMatchers(HttpMethod.GET, "/api/v1/feed").permitAll()
        .requestMatchers(HttpMethod.GET, "/api/v1/community/**").permitAll()
        .requestMatchers(HttpMethod.GET, "/api/v1/creators/**").permitAll()
        .requestMatchers(HttpMethod.GET, "/api/v1/topics/**").permitAll()
        .anyRequest().permitAll())
```

- `FOLLOWING` 无法在路由层按查询参数判断，必须在 Service 层校验。
- 所有接口支持可选 Token：JWT 过滤器解析成功即写入安全上下文；解析失败不会拦截公开接口。

### 11.2 Service 层校验

```java

        throw ApiException.unauthorized("UNAUTHORIZED", "请先登录");

```

- `FOLLOWING` 必须在任何数据库查询前校验，避免匿名请求触发关注表查询。
- 只读接口不校验会话是否被撤销（`AuthSessionGuard`）。理由：游客可访问，退出后的 Access Token 在有效期内仍可读取公开内容；写操作才需要会话校验。
- 若评审要求登录态严格校验，可在 `principal != null` 时调用 `guard.requireActive`，代价是每个登录请求多一次 Redis 查询。

### 11.3 内容安全

- 查询条件写死在 Repository 方法中，Controller/Service 不得传入状态。
- `findRecommendedCandidates` 必须包含 `published_at IS NOT NULL`，避免异常数据。
- 不返回作者联系方式、登录时间、状态。
- 日志只记录 `requestId`、`scope`、`limit`、结果条数、耗时，不记录正文与昵称。

### 11.4 参数安全

- `limit` 上下界裁剪在 Service 层完成，不依赖前端。
- `cursor` 长度 ≤ 256，解码异常统一转换为 `VALIDATION_ERROR`。
- 所有查询使用 MyBatis-Plus 条件构造器，禁止字符串拼接用户输入。
- `authorIds` 集合来自关注服务，数量过大时分批查询（单批 ≤ 500）。
