# C-53 私信与通知需求文档

> 版本：1.0｜日期：2026-10-26｜状态：实施前设计，尚未实现
> 面向：产品、研发、测试。范围：接口清单 G1–G6。
> 配套：[开发文档](../开发文档/私信与通知开发.md)、[设置与隐私需求](设置与隐私需求.md)。

## 1. 背景与目标

前端已有会话列表、聊天记录、文本发送、会话已读、通知列表和全部已读调用，但后端没有 conversations、messages、notifications 模块。当前消息页只能展示预置/已有会话，新增会话按钮没有业务事件；通知未读数也固定为 0。

目标：提供最小可用的站内文本私信和通知中心，具备权限检查、发送幂等、游标分页、未读数一致性和跨模块跳转能力。实时 WebSocket、附件消息和复杂社交通知不作为首期强制条件。

## 2. 用户和范围

### 本期范围

- 登录用户查看自己的会话列表和会话消息。
- 从用户主页或关注列表发起一对一文本会话，重复发起复用同一会话。
- 发送 `TEXT` 消息，使用 `clientMessageId` 幂等。
- 会话标记已读、通知列表、全部通知已读。
- 关注、评论、回复、分享等已实现模块通过事件生成站内通知；通知可携带目标类型和目标 ID。
- A11 `/auth/me` 返回真实 notifications/messages 未读数。

### 非本期范围

- 群聊、群管理、消息撤回/编辑、已读回执到消息级别。
- 图片、视频、语音、文件、表情和富文本消息。
- WebSocket/SSE 实时推送；首期允许页面进入时轮询或重新加载。
- 单条通知已读、通知删除、通知偏好细分、邮件/短信通知。
- 举报、拉黑发起流程；但读取和发送必须尊重拉黑关系。

## 3. 核心流程

### 3.1 发起和发送私信

1. 用户在成员主页或关系列表点击“发消息”。
2. 服务端验证当前用户、对方状态、私信权限、互相关系/关注关系和拉黑关系。
3. 若双方已有一对一会话，返回原会话；否则创建唯一会话。
4. 进入会话后加载消息，消息按创建时间倒序游标分页，前端按时间正序展示。
5. 发送文本，服务端校验并以 `clientMessageId` 去重；成功返回完整消息。
6. 接收方未读数加一，发送方会话列表更新时间和最后消息更新。

### 3.2 已读

进入会话并成功加载后调用 G4；服务端将当前用户在该会话中收到的消息标记已读，并减少 messages 未读总数。重复调用幂等。不能把“打开会话”当作对方已读，也不能清空所有通知。

### 3.3 通知

通知按创建时间倒序。每条至少包括 `id/actor/preview/createdAt/read`，建议增加 `type/targetType/targetId` 用于点击跳转。全部已读只影响当前用户通知，不删除内容、不影响消息未读数。

## 4. 接口需求

以下省略 `/api/v1`。

| 编号 | 方法与路径 | 规则 |
|---|---|---|
| G1 | GET `/conversations` | 需登录；返回 `items`，按 updatedAt 倒序 |
| G2 | GET `/conversations/{id}/messages` | 需登录；`limit` 默认 50、最大 100、`cursor`；仅会话成员可读 |
| G3 | POST `/conversations/{id}/messages` | 需登录；入 `clientMessageId/type/content`；201 新建或 200 幂等命中 |
| G4 | PUT `/conversations/{id}/read` | 需登录；204；仅当前成员生效 |
| G5 | GET `/notifications` | 需登录；`limit/cursor`；返回通知和 nextCursor |
| G6 | PUT `/notifications/read-all` | 需登录；204；当前用户全部未读通知已读 |

前端现有“+”入口需要新增创建会话接口。为了不改变已确认的 G1–G6，可增加 `POST /conversations`：入 `participantId`，返回会话；也可让 F4/F8 返回 conversationId，但不得让前端伪造会话 ID。产品应优先采用 `POST /conversations`。

统一错误：`CONVERSATION_NOT_FOUND`、`NOT_CONVERSATION_MEMBER`、`MESSAGE_NOT_ALLOWED`、`MESSAGE_TOO_LONG`、`DUPLICATE_MESSAGE`（仅在幂等键内容不一致时）、`NOTIFICATION_NOT_FOUND`、`RATE_LIMITED`。

## 5. 数据和规则

- 会话是一对一，成员排序后的二元组唯一；不能通过请求重复创建多条。
- 消息正文纯文本，去首尾空白，长度 1–2000 Unicode 码点，拒绝非法控制字符和 HTML 执行；换行可保留。
- `type` 当前仅 `TEXT`。未知类型拒绝，不静默降级为文本。
- `clientMessageId` 由客户端生成，最大 64 字符；同一发送者在同一会话唯一。相同幂等键且正文/类型相同返回原消息；相同键内容不同返回 409。
- 已删除/停用账号不可发新消息；历史消息按产品策略显示“账号已不可用”，不暴露已删除用户的私有资料。
- 会话列表展示 participant、lastMessage、updatedAt、unreadCount；lastMessage 对无权限或删除消息做脱敏。
- 通知预览不包含密码、验证码、联系方式等敏感内容；actor 和目标必须再次做可见性过滤。
- 通知未读数和消息未读数分别统计；G4 不得清理通知。

## 6. 权限和隐私

- 游客不能读取会话、消息或通知。
- `social.messages`：EVERYONE 允许；FOLLOWING 要求接收方关注发送方；MUTUAL 要求互相关注；NONE 拒绝新会话/新消息。规则以接收方设置为准。
- 任一方拉黑后禁止新消息，已有会话至少隐藏发送入口；是否保留历史由隐私模块统一决定。
- 仅返回当前用户有权看到的会话和消息；不能通过猜测 ID 越权枚举资源，建议对不存在和无权限使用同类提示。
- 通知目标被删除或不可见时仍可保留通用预览，但点击不能绕过权限。

## 7. 性能和可靠性

- 会话/消息分页接口 P95 ≤ 300ms，通知列表 P95 ≤ 300ms。
- 发送幂等命中必须在 200ms 级别返回，不能重复发通知或增加未读数。
- 消息写入、会话摘要更新、接收方未读增加和消息通知事件必须保证最终一致；主消息成功不能因通知失败而回滚。
- 页面首期可进入时加载；接口应返回 nextCursor，便于后续轮询或实时升级。
- 消息发送限流按用户和会话设置，命中后返回 retryAfter；不能因 Redis 故障无界放行。

## 8. 验收标准

- [ ] 两名允许互发的用户可以创建唯一会话、加载消息并发送文本。
- [ ] 重复创建会话得到同一会话；重复发送同一幂等请求不重复消息、不重复通知。
- [ ] 相同 clientMessageId 不同正文返回冲突，不能覆盖原消息。
- [ ] 非成员、游客、被拉黑或不满足消息设置的请求均被拒绝。
- [ ] 消息列表 cursor 稳定，刷新后顺序不跳变，空会话状态正确。
- [ ] 打开会话只清除当前会话收到的未读消息；G5 通知未读独立保留。
- [ ] 关注/评论/回复触发通知，通知 actor、预览和目标可正确展示或安全降级。
- [ ] A11 未读数与会话/通知列表的已读结果最终一致。
- [ ] 消息和通知不泄露隐私设置、联系方式、验证码和不可见动态。
- [ ] 服务重试、数据库唯一键冲突和通知队列重复消费不会产生重复消息/未读。

## 9. 依赖和交付

依赖个人资料/关注关系、设置/隐私、互动事件和统一会话校验。交付包含消息表、会话表、通知表、幂等约束、G1–G6、创建会话接口、A11 未读数接入、前端入口补齐和端到端测试。
