## 2. 背景与目标

### 2.1 现状

- 前端 `App.vue` 在 `loadPublicData()` 中并发请求四个接口：`GET /feed`、`GET /topics/trending`、`GET /creators/recommended`、`GET /community/summary`，使用 `Promise.allSettled`，任一失败只做局部降级。
- 后端 `topic` 模块已实现 `GET /api/v1/topics/trending`，返回 `id`、`name`、`postCount`。
- 后端 `post` 模块已实现发布、草稿、定时、详情、我的发布，`posts`、`topics`、`media_assets` 三张表已建。
- `GET /feed`、`GET /creators/recommended`、`GET /community/summary` 三个接口后端不存在，前端当前请求会得到 404，首页信息流为空。
- `SecurityConfig` 当前对未知路径统一 `permitAll()`，新接口默认公开；JWT 过滤器会对携带 Token 的请求解析身份，但匿名请求也可通过。
- 前端未登录时也可以点击「正在关注」标签，`loadFeed()` 没有登录拦截，会直接请求 `scope=FOLLOWING`。
- `PostResponse` 已包含 `author`、`topic`、`content`、`summary`、`media` 等字段，但**没有** `likeCount`、`likedByMe`、`bookmarkedByMe`、`commentCount`；前端 `normalizePost` 对缺失字段兜底为 0 / false。
- `UserSummary` 只有 `id`、`nickname`、`username`、`initials`、`avatarUrl`、`profession`，**没有** `relationship`，前端 `normalizeUser` 对关注状态兜底为未关注。
- 关注表与互动表尚未实现，属于接口清单 3.6 与 3.4 模块。

### 2.2 问题

1. 首页没有真实内容，用户登录后看不到任何动态，产品闭环断裂。
2. 「为你推荐 / 正在关注 / 最新发布」三个标签没有后端语义，无法区分。
3. 热门话题接口虽然存在，但**字段名不匹配**：后端返回 `postCount`，前端 `normalizeTopic` 读取 `discussionCount ?? count`，导致首页、侧边栏、发现页的话题讨论数恒为 0。
4. 推荐创作者、在线人数没有数据来源，首页右侧栏与侧边栏缺少内容。
5. 未登录用户点击「正在关注」会收到 401，页面直接显示错误，没有登录引导。
6. 访客与登录用户的可见范围没有明确规定，存在草稿或定时内容被错误分发的风险。
7. 列表没有排序与分页规则，后续内容量上来后容易出现重复、跳条、深分页。

### 2.3 目标

| 类型 | 目标 |
|---|---|
| 业务目标 | 首页稳定展示公开内容，形成「浏览 → 进入详情 → 关注 / 互动」的入口 |
| 产品目标 | 三种信息流有明确差异；热门话题与推荐创作者能持续轮换，不长期固定 |
| 体验目标 | 首屏在 1 秒内可见内容；空态、错误态、登录态有明确区分 |
| 技术目标 | 列表只返回公开内容；游标分页不重复不遗漏；匿名可读、写操作必须登录 |
| 可衡量指标 | Feed 接口成功率 ≥ 99.5%；P95 ≤ 150ms；发布后 ≤ 2 秒出现在「最新」首屏；话题计数与已发布动态数偏差 ≤ 0.1% |

### 2.4 成功标准

- 游客打开首页能看到公开动态、热门话题、推荐创作者；不出现草稿或定时内容。
- 登录用户在「为你推荐」「正在关注」「最新发布」之间切换，三者的内容或顺序有可感知差异，且不出现明显重复。
- 未登录点击「正在关注」时被引导登录，不出现直接报错。
- 首页话题的讨论数与实际已发布动态数一致。
- 侧边栏在线人数随真实活跃变化，Redis 故障时页面仍能正常打开。
- 推荐创作者不包含自己、不包含已关注用户（登录态）。

## 3. 用户角色与场景

### 3.1 角色

| 角色 | 定义 | 在本模块的权限 |
|---|---|---|
| 游客 | 未登录访问者 | 浏览推荐流、最新流、热门话题、推荐创作者、在线人数；不能请求关注流 |
| 登录用户 | 已认证的 `ACTIVE` 用户 | 在游客能力基础上，可请求关注流；推荐创作者排除自己与已关注 |
| 作者 | 某条动态的创建者 | 其公开动态可进入信息流；草稿与定时内容不进入任何流 |
| 被拉黑用户 | 与当前用户存在拉黑关系 | 其内容与推荐位对当前用户不可见（依赖 3.8 设置模块） |
| 管理员 | 本期不存在 | 无后台、无审核、无强制下线（范围外） |

> 拉黑过滤依赖 3.8 模块，本期若未上线，先预留过滤接口，行为等同于不过滤。

### 3.2 核心场景

| 场景 | 前置 | 主流程 | 结果 |
|---|---|---|---|
| S1 游客浏览首页 | 未登录 | 打开首页 → 加载推荐流 → 浏览话题与推荐创作者 | 看到公开内容；「正在关注」不可用或点击后弹登录 |
| S2 登录用户切换信息流 | 已登录 | 点击「正在关注」→ 请求 `scope=FOLLOWING` | 看到所关注作者的公开动态；无关注时显示引导 |
| S3 发布后回到首页 | 已发布 | 发布成功 → 返回首页 → 切到「最新发布」 | 新动态出现在首位 |
| S4 浏览推荐创作者 | 未登录 / 已登录 | 首页右栏或发现页浏览 → 点击关注 | 关注成功，按钮变为「已关注」，列表不重新拉取 |
| S5 进入热门话题 | 任意 | 点击话题 | 本期只做视觉反馈或跳转发现页；话题详情页不在本期范围 |
| S6 在线人数展示 | 任意 | 打开任意页面 | 侧边栏显示「N 人在线」；N 为 0 时整块隐藏 |
| S7 服务降级 | 任意 | Redis 或推荐服务异常 | 在线人数显示 0；信息流仍可加载；不阻塞首页 |

### 3.3 用户故事

- 作为游客，我希望不登录也能看到社区里正在发生的内容，从而决定是否加入。
- 作为登录用户，我希望「正在关注」只展示我关注的人，而不是和推荐流一样。
- 作为登录用户，我希望首页不会给我推荐我自己，也不会反复推荐我已经关注的人。
- 作为作者，我希望我的草稿和定时内容不会出现在任何人的首页。
- 作为读者，我希望列表加载失败时有明确的提示和重试入口，而不是一片空白。
- 作为产品运营，我希望热门话题与推荐创作者会自然轮换，不需要人工每天调整。

## 4. 名词与口径

| 名词 | 定义 |
|---|---|
| 公开动态 | `status = PUBLISHED` 且 `deleted_at IS NULL` 的动态 |
| 可见动态 | 在当前请求身份下允许展示的公开动态（叠加拉黑、可见性等过滤） |
| 推荐流 | `scope=RECOMMENDED`，按推荐得分排序的公开动态 |
| 关注流 | `scope=FOLLOWING`，仅当前用户所关注作者发布的公开动态，必须登录 |
| 最新流 | `scope=LATEST`，按 `published_at` 倒序的公开动态 |
| 首屏 | 单次请求返回的 `limit` 条内容，本期前端固定请求 20 条 |
| 游标 | 服务端返回的 `nextCursor`，用于续页；本期前端暂不使用 |
| 热门话题 | 状态为 `ACTIVE`、按已发布动态数倒序的话题 |
| 推荐创作者 | 按活跃度、资料完整度等规则排序的公开用户摘要 |
| 在线人数 | 最近 5 分钟内有已认证请求的去重登录用户数（详见 6.4） |
| 半衰期 | 推荐得分中时间因素的衰减速度，本期取 24 小时 |

## 6. 功能需求

### 6.1 首页信息流（`GET /feed`）

#### 6.1.1 范围与入口

前端三个标签与 `scope` 的映射固定为：

| 前端标签 | `scope` | 鉴权 | 说明 |
|---|---|---|---|
| 为你推荐 | `RECOMMENDED` | 可选登录 | 默认值；未传 `scope` 时按此处理 |
| 正在关注 | `FOLLOWING` | 必须登录 | 未登录请求返回 401；前端应先拦截并引导登录 |
| 最新发布 | `LATEST` | 可选登录 | 按发布时间倒序 |

- `scope` 取值不区分大小写，服务端统一转大写。
- 非法 `scope` 返回 `400 VALIDATION_ERROR`。
- 切换标签时前端重新请求；不使用缓存结果拼接。

#### 6.1.2 可见性过滤（强制）

所有 scope 都必须满足：

1. `status = 'PUBLISHED'`。
2. `deleted_at IS NULL`。
3. 作者状态为 `ACTIVE`；作者被禁用或删除后，其内容不再进入信息流。
4. 命中当前用户拉黑关系的内容不返回（依赖 3.8，本期预留）。
5. 定时动态在到达 `scheduled_at` 前为 `SCHEDULED` 状态，不得出现；到达后由定时任务转为 `PUBLISHED` 才可进入。
6. 内容为空或正文仅有空白的异常数据不进入信息流。

> 任何情况下，信息流都不返回 `DRAFT`、`SCHEDULED`、`DELETED` 状态的数据。作者本人也不通过 `/feed` 看到自己的草稿；草稿只在 `/me/posts` 与 `/posts/{id}` 返回。

#### 6.1.3 推荐流规则（`RECOMMENDED`）

**候选池**

- 最近 7 天内发布（`published_at >= now - 7d`）的公开动态。
- 候选数量上限 500 条；不足时按实际数量处理。
- 同一作者连续出现不超过 2 条（同作者第 3 条及以后先跳过，若候选不足则放宽）。

**得分公式（v1）**

```
score = 0.60 × timeScore + 0.25 × topicScore + 0.15 × authorScore
```

| 因子 | 计算方式 | 说明 |
|---|---|---|
| `timeScore` | `exp(-ageHours / 24)` | 半衰期约 16.6 小时；7 天前的动态接近 0 |
| `topicScore` | `topic.postCount / max(postCount)` | 候选池内归一化；无话题为 0 |
| `authorScore` | 资料完整度：头像 0.4 + 简介 0.3 + 职业 0.3 | 无资料为 0 |

- 互动数据上线后，公式调整为：
  `score = 0.40 × timeScore + 0.35 × engagementScore + 0.15 × topicScore + 0.10 × authorScore`，
  其中 `engagementScore = log1p(3 × likeCount + 5 × commentCount + 4 × bookmarkCount)`，候选池内归一化。
- 本期互动为 0 时不得除以 0；`engagementScore` 整体不参与计算。

**其他规则**

- 自己的动态可以出现在推荐流（便于用户确认发布结果），但「最新发布」已能覆盖该需求；**默认排除自己**，待评审确认（见第 17 章）。
- 已关注作者的动态在推荐流中不做排除，但同作者密度受 6.1.3 限制。
- 推荐流每次请求允许重新计算；本期不做跨请求稳定快照。

#### 6.1.4 关注流规则（`FOLLOWING`）

- 必须登录；未登录返回 `401 UNAUTHORIZED`，文案「请先登录」。
- 只返回当前用户关注列表中作者的公开动态。
- 不包含自己的动态。
- 排序：`published_at DESC, id DESC`。
- 关注列表为空时返回空列表，前端显示「还没有关注任何人」引导，而不是错误。
- 依赖 3.6 关注表；未上线时返回空列表，不返回 404。

#### 6.1.5 最新流规则（`LATEST`）

- 排序：`published_at DESC, id DESC`。
- 不排除自己；登录与游客结果一致（未来若引入可见性设置再调整）。
- 适合作为“发布后确认”的入口。

#### 6.1.6 分页与游标

| 项目 | 规则 |
|---|---|
| `limit` | 缺省 20；`<= 0` 按 20 处理；`> 50` 截断为 50 |
| `cursor` | 可选；为空表示第一页 |
| 返回 | `{ "items": [...], "nextCursor": "..." 或 null }` |
| 续页判定 | 多查 1 条，存在第 `limit + 1` 条时返回 `nextCursor` |
| 游标内容 | `LATEST` / `FOLLOWING`：`published_at + id`，复用 `CursorCodec` |
| 推荐流游标 | v1 返回 `null`，因为推荐分依赖实时计算，跨请求无法保证稳定；v2 引入快照游标 |
| 非法游标 | 返回 `400 VALIDATION_ERROR`，文案「分页游标不合法」 |
| 游标长度 | 超过 256 字符直接拒绝 |

> 前端当前只传 `limit`，不传 `cursor`。本期接口必须支持 `cursor` 并返回 `nextCursor`，但前端不消费；无限滚动列入后续迭代。

#### 6.1.7 空态、错误态与加载态

| 状态 | 前端表现 | 后端要求 |
|---|---|---|
| 加载中 | 「正在加载内容」 | 正常处理 |
| 空列表 | 「这里暂时还是空的」；`FOLLOWING` 显示关注引导 | 返回 200 + 空数组，不返回 404 |
| 请求失败 | 「内容暂时无法加载」+ 错误文案 | 返回统一错误结构 |
| 未登录请求关注流 | 先弹登录，不发起请求 | 若仍收到请求，返回 401 |

- 首页四个接口**互不阻塞**：`/feed` 失败不影响话题、创作者、在线人数展示。
- `/feed` 重试建议前端提供「重试」按钮；本期可用刷新页面代替，不强制。

#### 6.1.8 列表项字段（PostView）

信息流复用现有 `PostResponse`，并**补三个前端已消费、后端暂缺的字段**：

| 字段 | 类型 | 本期取值 | 说明 |
|---|---|---|---|
| `likeCount` | number | `0` | 互动模块上线后填真实值 |
| `likedByMe` | boolean | `false` | 未登录恒为 false |
| `bookmarkedByMe` | boolean | `false` | 未登录恒为 false |
| `commentCount` | number | `0` | 互动模块上线后填真实值 |

- 这几个字段即使暂时为 0 / false，也必须在响应中**存在**，避免前端字段缺失导致的契约漂移。
- `summary` 由服务端生成，最多 120 个码点，超出以「…」结尾；前端列表正文优先使用 `summary`。
- `content` 返回完整正文（最多 600 码点），供详情页直接使用；列表页不展开。
- `media` 按 `sortOrder` 升序；列表页最多展示前 3 个，其余由前端显示「＋N」。
- `displayTime` 可选，本期不返回，前端回退展示 `createdAt`。

### 6.2 热门话题（`GET /topics/trending`）

#### 6.2.1 排序与数量

- 只返回 `status = 'ACTIVE'` 的话题。
- 排序：`post_count DESC, id ASC`；`id` 作为稳定次序，避免同计数时顺序抖动。
- `limit` 缺省 10，范围 1～50；超过 50 截断为 50，小于 1 按 1 处理。
- 不走分页，一次性返回。

#### 6.2.2 计数口径与更新时机

`post_count` 表示**该话题下当前处于 `PUBLISHED` 状态的动态数**，不含草稿、定时、已删除内容。

现有实现的更新点已覆盖：

| 操作 | 计数变化 | 现状 |
|---|---|---|
| 发布时直接创建为 `PUBLISHED` | +1 | 已实现 |
| 草稿立即发布 | +1 | 已实现 |
| 定时任务到点发布 | +1 | 已实现 |
| 已发布动态修改话题 | 旧话题 -1，新话题 +1 | 已实现 |
| 删除已发布动态 | -1 | 已实现 |
| 草稿转定时、定时改期、取消定时 | 不变化（未公开） | 已实现 |

要求：

- 计数更新与动态状态变更在**同一事务**内，失败一起回滚。
- 并发发布不会重复 +1；现有条件更新已保证。
- 计数为负时按 0 处理，不向前端返回负数。

#### 6.2.3 字段契约修正（重要）

现状差异：

- 后端返回：`{ "id", "name", "postCount" }`。
- 前端 `App.vue` 的 `normalizeTopic` 读取：`topic.discussionCount ?? topic.count ?? 0`。
- 结果：**首页、侧边栏、发现页的话题讨论数全部显示 0**。

处理方案（推荐）：保持后端字段 `postCount` 不变，修改前端 `normalizeTopic` 为：

```js
count: String(topic.postCount ?? topic.discussionCount ?? topic.count ?? 0)
```

理由：接口清单已把 `postCount` 定为标准字段，后端和数据库字段一致；前端只需兼容一次。

若评审选择后端兼容，则后端额外返回 `count` 别名，但需在接口文档中标记为兼容字段，并在下一个版本移除。

#### 6.2.4 展示与缓存

- 首页右栏展示全部返回项（当前最多 10 条）。
- 侧边栏只展示前 3 条。
- 发现页展示全部。
- 本期不加缓存；查询走 `idx_topics_status_count`，数据量小。QPS 上升后再加 60 秒缓存。

### 6.3 推荐创作者（`GET /creators/recommended`）

#### 6.3.1 候选池与排除规则

| 规则 | 游客 | 登录用户 |
|---|---|---|
| 只取 `status = 'ACTIVE'` 用户 | 是 | 是 |
| 排除自己 | — | 是 |
| 排除已关注用户 | — | 是（依赖 3.6） |
| 排除拉黑用户 | — | 是（依赖 3.8） |
| 排除无昵称 / 异常用户 | 是 | 是 |
| 资料为空但账号正常 | 保留，但排序靠后 | 同左 |

#### 6.3.2 排序规则（v1）

```
score = 0.40 × activityScore + 0.30 × followerScore + 0.20 × profileScore + 0.10 × randomScore
```

| 因子 | 计算方式 | 缺失时 |
|---|---|---|
| `activityScore` | 近 30 天公开动态数，候选池内归一化 | 0 |
| `followerScore` | 粉丝数，候选池内归一化 | 0（关注模块未上线） |
| `profileScore` | 头像 0.4 + 简介 0.3 + 职业 0.3 | 0 |
| `randomScore` | `[0,1)` 随机数 | 始终可用 |

- `randomScore` 权重固定 10%，用于让列表自然轮换，避免长期只推同几个人。
- 同一用户在同一缓存周期内位置稳定；缓存过期后重新计算。
- 不做个性化（不基于浏览行为），本期只区分登录 / 游客。

#### 6.3.3 数量与返回结构

- 固定返回 **6 条**（不足时返回实际数量）。
- 响应结构：

```json
{
  "items": [
    {
      "id": "usr_xxx",
      "nickname": "沈闻",
      "username": "shenwen",
      "avatarUrl": "",
      "initials": "沈",
      "profession": "独立摄影师",
      "relationship": "NONE"
    }
  ]
}
```

- 前端首页右栏建议只展示 3 条（前端可 `slice(0, 3)`），发现页展示全部 6 条。
- 本期不返回 `followerCount`、`postCount` 等扩展字段；若后续展示“共同关注”再补。

#### 6.3.4 `relationship` 字段

- 取值：`FOLLOWING` / `FOLLOWED_BY` / `MUTUAL` / `NONE`。
- 游客一律返回 `NONE`。
- 登录用户由关注关系计算；关注模块未上线时返回 `NONE`。
- 前端据此决定按钮文案与状态；关注操作成功后前端原地更新，不重新拉取列表。

#### 6.3.5 缓存与降级

- 公共候选池缓存 5 分钟（Redis，key 见 8.3），缓存内容为按得分排序的前 100 名用户 ID。
- 请求时在应用层做「排除自己 / 已关注 / 拉黑」过滤，再取前 6 条。
- 缓存不可用时直接查库，接口仍返回 200。
- 无任何可用用户时返回 `{ "items": [] }`；首页右栏整块不显示。

### 6.4 社区概况与在线人数（`GET /community/summary`）

#### 6.4.1 本期返回

```json
{ "onlineCount": 28 }
```

- 本期只返回 `onlineCount`；后续新增字段必须保持向后兼容。
- 前端按数字兜底：缺失、非数字、负数都显示 0。
- 不返回用户名单、地区、设备等任何可识别信息。

#### 6.4.2 在线口径

**定义：最近 5 分钟内发起过至少一次已认证 API 请求的去重登录用户数。**

- 只统计登录用户；游客不计入。
- 同一用户在 5 分钟窗口内只计 1 次。
- 用户退出登录后，最多残留 5 分钟。
- 同一用户 60 秒内最多写一次 Redis，降低写放大。
- 计数允许 ±5% 误差；不要求精确到秒，不做实时推送。

#### 6.4.3 实现方式（建议）

| 项目 | 方案 |
|---|---|
| 存储 | Redis ZSET：`c53:community:online`，`member = userId`，`score = 当前毫秒时间戳` |
| 写入 | `JwtAuthenticationFilter` 认证成功后写入；`ZADD` + `ZREMRANGEBYSCORE` 清理 5 分钟前成员 |
| 写入节流 | 进程内 `Caffeine` 或简单 Map 记录 `userId -> lastWriteAt`，60 秒内跳过；多实例允许各自节流 |
| 查询 | `ZCOUNT key (now - 5min) +inf` |
| 清理 | 写入时顺带清理；查询不做全量清理，避免大 key 阻塞 |
| 多实例 | 共享同一 Redis，天然聚合 |
| 失败处理 | 写入失败只记 `warn`，不影响请求；查询失败返回 `onlineCount = 0` |
| 超时 | Redis 操作超时 50ms，避免拖慢鉴权链路 |

> 若评审认为在鉴权过滤器写 Redis 影响面过大，可改为独立的轻量心跳接口（前端每 60 秒调用一次）。但会增加前端改动与请求量，本期推荐过滤器方案。

#### 6.4.4 展示规则

- 侧边栏：`onlineCount > 0` 时显示「N 人在线」；为 0 时整块隐藏。
- 首页其他位置当前不展示在线人数。
- 文案固定，不做“约”“+”。

#### 6.4.5 失败与降级

| 情况 | 行为 |
|---|---|
| Redis 不可用 | 返回 200，`onlineCount = 0` |
| 统计数据异常（负数、超大值） | 负数归 0；超过 100 万视为异常，返回 0 并记录告警 |
| 接口超时 | 前端 `allSettled` 降级为 0，不影响其他模块 |

## 7. 排序、分页与一致性规则

### 7.1 排序键汇总

| 数据 | 主排序 | 次排序 | 稳定性 |
|---|---|---|---|
| 推荐流 | `score` 降序 | `published_at` 降序、`id` 降序 | 单次请求内稳定 |
| 关注流 | `published_at` 降序 | `id` 降序 | 跨请求稳定 |
| 最新流 | `published_at` 降序 | `id` 降序 | 跨请求稳定 |
| 热门话题 | `post_count` 降序 | `id` 升序 | 跨请求稳定 |
| 推荐创作者 | `score` 降序 | `id` 升序 | 缓存周期内稳定 |

### 7.2 游标格式

- 复用 `CursorCodec`：`Base64Url(epochMillis + "|" + id)`。
- 解码后用于 `(published_at, id) < (cursorTime, cursorId)` 的复合条件。
- 游标字段必须与排序字段一致；`FOLLOWING` 与 `LATEST` 均使用 `published_at`。
- 推荐流本期返回 `nextCursor = null`。
- 游标不做签名；因为只包含时间与 ID，无法借此越权。需限制长度并校验 ID 格式。

### 7.3 一致性窗口

| 事件 | 要求 |
|---|---|
| 发布成功 | ≤ 2 秒内出现在「最新发布」首屏 |
| 删除成功 | ≤ 2 秒内从所有信息流消失（软删后查询即过滤） |
| 定时到点 | 定时任务扫描周期内（当前 ≤ 60 秒）转入公开 |
| 话题计数 | 与发布/删除同事务，实时一致 |
| 在线人数 | 最多 60 秒延迟，登出后最多残留 5 分钟 |

### 7.4 去重

- 同一请求内按动态 ID 去重。
- 推荐流限制同作者连续出现次数。
- 前端切换标签时整体替换列表，不与旧列表合并。

### 8.2 索引

|---|---|---|
| `idx_posts_feed (status, published_at, id)` | 最新流 | 已存在 |
| `idx_posts_topic_published (topic_id, status, published_at)` | 话题下动态（后续） | 已存在 |

关注流实现建议：

1. 先查关注关系得到作者 ID 列表（依赖 3.6）。
2. 使用 `author_id IN (...) AND status = 'PUBLISHED' AND deleted_at IS NULL` 查询，按 `published_at DESC, id DESC` 排序。
3. 作者数量过多时改为 `JOIN follows`，避免 `IN` 列表过长。

### 8.3 Redis 键

| Key | 类型 | TTL | 用途 |
|---|---|---|---|
| `c53:community:online` | ZSET | 无（滑动清理） | 在线用户 |
| `c53:creators:recommended:pool` | String（JSON） | 5 分钟 | 推荐创作者候选池 |
| `c53:rate:feed:ip:{ip}` | String | 1 分钟 | 匿名限流 |
| `c53:rate:feed:user:{userId}` | String | 1 分钟 | 登录限流 |

- 键前缀统一 `c53:`，便于监控与批量清理。
- 不缓存用户隐私数据；推荐池只存用户 ID 与得分。

### 8.4 数据约定

- 时间统一 UTC，接口输出 ISO 8601。
- 动态 ID 前缀 `pst_`，用户 `usr_`，话题 `tpc_`。
- 所有列表查询显式过滤 `deleted_at IS NULL`。

## 9. 接口需求

### 9.1 通用约定

- 前缀 `/api/v1`，响应统一 `{ code, data, requestId }`。

- 不返回粉丝数、动态数等扩展字段。
- 无可用用户时返回 `{ "items": [] }`。

**错误**

| 状态 | code | 场景 |
|---|---|---|
| 429 | `RATE_LIMITED` | 超过限流阈值 |
| 503 | `SERVICE_UNAVAILABLE` | 数据库不可用 |

### 9.4 错误码汇总

| code | HTTP | 含义 | 前端处理 |
|---|---|---|---|
| `VALIDATION_ERROR` | 400 | 参数非法 | 显示 `message` |
| `UNAUTHORIZED` | 401 | 未登录 | 引导登录 |
| `RATE_LIMITED` | 429 | 请求过频 | 显示「操作过于频繁，请稍后再试」 |
| `SERVICE_UNAVAILABLE` | 503 | 依赖不可用 | 显示「服务暂时不可用，请稍后重试」 |
| `INTERNAL_ERROR` | 500 | 未预期异常 | 显示通用错误 |

### 9.5 与现有实现的差异与改造点

| # | 差异 | 影响 | 改造 |
|---|---|---|---|
| 1 | B1、B2、B4 后端不存在 | 首页空 | 新增 `community`、`feed`、`creator` 相关控制器与服务 |
| 2 | B3 返回 `postCount`，前端读 `count` | 话题讨论数恒为 0 | 修改前端 `normalizeTopic`（推荐）或后端兼容 |
| 3 | `PostResponse` 缺互动字段 | 前端兜底 0 / false | 在 `PostResponse` 增加 `likeCount`、`likedByMe`、`bookmarkedByMe`、`commentCount` |
| 4 | `UserSummary` 缺 `relationship` | 关注按钮状态错误 | B4 单独定义带 `relationship` 的视图，或扩展 `UserSummary` |
| 5 | 前端未拦截未登录的 `FOLLOWING` | 直接报 401 | `loadFeed()` 前校验登录，弹登录框 |
| 6 | `SecurityConfig` 默认 `permitAll` | 新接口默认公开 | 明确 `/feed`、`/creators/recommended` 公开；`FOLLOWING` 在 Controller 内校验 |
| 7 | 缺关注流索引 | 查询变慢 | 新增 `idx_posts_author_status_published` |
| 8 | 无在线统计 | 侧边栏空白 | 新增 Redis ZSET 统计与 `community/summary` |

## 10. 权限、安全与风控

### 10.1 鉴权矩阵

| 接口 | 游客 | 登录用户 | 说明 |
|---|---|---|---|
| `GET /community/summary` | 允许 | 允许 | 只返回总数 |
| `GET /feed?scope=RECOMMENDED` | 允许 | 允许 | 登录态可能影响拉黑过滤 |
| `GET /feed?scope=LATEST` | 允许 | 允许 | — |
| `GET /feed?scope=FOLLOWING` | 401 | 允许 | — |
| `GET /topics/trending` | 允许 | 允许 | — |
| `GET /creators/recommended` | 允许 | 允许 | 登录态排除自己与已关注 |

### 10.2 内容泄露防护

- 信息流查询条件强制包含 `status = 'PUBLISHED'` 与 `deleted_at IS NULL`，**不得**依赖调用方传入状态。
- 作者本人也不能通过 `/feed` 获取自己的草稿；草稿入口只有 `/me/posts` 与 `/posts/{id}`。
- 定时动态在转正前不进入任何信息流。
- 被禁用用户的公开内容默认不再分发；是否保留历史内容由运营策略决定，本期按“不分发”处理。
- 拉黑过滤为双向：A 拉黑 B 后，A 不看到 B，B 也不看到 A（依赖 3.8）。
- 接口不返回作者的联系方式、邮箱、手机号、登录时间等字段。

### 10.3 限流

| 接口 | 维度 | 阈值（建议） | 超限 |
|---|---|---|---|
| `/feed` | IP（匿名） | 60 次/分钟 | 429 |
| `/feed` | userId（登录） | 120 次/分钟 | 429 |
| `/creators/recommended` | IP | 30 次/分钟 | 429 |
| `/community/summary` | IP | 60 次/分钟 | 429 |
| `/topics/trending` | IP | 30 次/分钟 | 429 |

- 复用现有 `RedisRateLimiter`，键见 8.3。
- Redis 故障时放行，不因限流组件故障阻断首页。
- 前端对 429 只提示，不自动重试。

### 10.4 缓存与隐私

- 在线统计只存用户 ID 与时间戳，不存 IP、设备、位置。
- 推荐池只存用户 ID 与得分。
- 缓存内容不含正文、手机号、邮箱等敏感字段。
- Redis 键不包含可读的用户名，仅使用内部 ID。

### 10.5 游标与参数安全

- `limit` 必须做上下界裁剪，防止一次拉取过多数据。
- `cursor` 限制长度 ≤ 256，解码失败返回 400。
- 所有查询参数使用绑定变量，禁止字符串拼接 SQL。
- 推荐流候选池上限 500，防止全表扫描。

## 11. 非功能需求

### 11.1 性能

| 指标 | 目标 |
|---|---|
| `/feed` P95 | ≤ 150ms（不含网络） |
| `/feed` 缓存命中 P95 | ≤ 50ms |
| `/creators/recommended` P95 | ≤ 100ms（缓存命中 ≤ 30ms） |
| `/topics/trending` P95 | ≤ 50ms |
| `/community/summary` P95 | ≤ 30ms |
| 单次响应体 | ≤ 512KB（20 条、每条最多 9 个媒体） |

- 禁止 N+1 查询；作者、话题、媒体均批量加载。
- 推荐流候选池上限 500，避免大结果集排序。

### 11.2 可用性与降级

| 故障 | 行为 |
|---|---|
| Redis 不可用 | 在线人数返回 0；限流放行；推荐池缓存穿透查库 |
| 数据库不可用 | `/feed`、`/topics/trending`、`/creators/recommended` 返回 503；`/community/summary` 仍返回 200 + 0 |
| 媒体签名失败 | `media.url` 为空或占位，不阻塞列表 |
| 单个子接口失败 | 首页其余模块正常展示 |

### 11.3 容量假设

| 项目 | 假设 |
|---|---|
| 日活用户 | 1 万 |
| 动态总量 | 100 万 |
| 每日新增动态 | 5000 |
| 在线人数峰值 | 2000 |
| 推荐候选池 | 500 条/次 |
| Redis 在线 ZSET 大小 | ≤ 峰值在线数 × 1.2 |

### 11.4 可观测性

| 指标 | 说明 |
|---|---|
| `feed_requests_total{scope,result}` | 按范围与结果统计 |
| `feed_latency_seconds` | P50 / P95 / P99 |
| `feed_cache_hit_total` | 缓存命中（如启用） |
| `community_online_count` | 当前在线人数 Gauge |
| `creators_pool_refresh_total` | 推荐池刷新次数与耗时 |
| 日志 | 记录 `requestId`、`scope`、`limit`、耗时、结果条数；不记录正文 |

- 接口成功率 < 99% 或 P95 > 300ms 持续 5 分钟触发告警。
- Redis 写入失败率 > 1% 触发告警。

### 11.5 时区与时间

- 数据库存 UTC，接口输出 ISO 8601。
- 时间衰减、在线窗口均使用服务端时钟。
- 前端展示相对时间或本地时间，不在服务端生成「几分钟前」。

## 12. 前端交互需求

### 12.1 涉及文件

| 文件 | 改动 |
|---|---|
| `src/App.vue` | `loadFeed()` 增加登录拦截；`normalizeTopic` 读取 `postCount`；错误态区分；`onlineCount` 保持；推荐创作者 `slice` 展示 |
| `src/services/api.js` | 无需新增方法；确认 `getFeed`、`getTopics`、`getRecommendedCreators`、`getCommunitySummary` 参数与路径不变 |
| `src/components/feed/FeedView.vue` | 未登录时「正在关注」点击引导登录；空态文案；首页右栏创作者建议只展示 3 条 |
| `src/components/discover/DiscoverView.vue` | 话题卡片当前无点击行为，本期保持；创作者展示 6 条 |
| `src/components/layout/AppSidebar.vue` | 在线人数展示逻辑不变（>0 显示） |

### 12.2 交互规则

1. **未登录点击「正在关注」**：不发起请求，直接打开登录弹窗；登录成功后自动切回并加载关注流。
2. **信息流切换**：点击标签后立即进入加载态；失败时保留旧列表还是清空？本期按“清空并展示错误”处理，与现有 `loadFeed` 一致。
3. **关注按钮**：点击后使用接口返回的 `following` / `followsMe` 原地更新；失败回滚并提示。
4. **话题点击**：本期跳转发现页（现有行为），不新增话题详情页。
5. **在线人数**：不轮询、不自动刷新；页面刷新时更新。
6. **空态**：
   - 推荐流为空：「这里暂时还是空的」。
   - 关注流为空：「还没有关注任何人，去发现页看看吧」+ 跳转按钮。
   - 推荐创作者为空：首页右栏整块隐藏。
   - 热门话题为空：右栏话题卡片隐藏或显示空态。
7. **错误文案**：直接使用后端 `message`；网络错误使用前端兜底文案。

### 12.3 兼容与降级

- 四个接口使用 `Promise.allSettled`，互不影响。
- `onlineCount` 缺失或非数字时显示 0，并且不显示侧边栏在线块。
- `topics` 为空时，发布框的话题下拉为空；前端需保证不提交空 `topicId`（发布模块已校验）。
- `people` 为空时，首页右栏「值得认识的人」不渲染。
- 后端字段 `postCount` 统一后，前端删除对 `discussionCount` 的依赖，但保留兜底。
